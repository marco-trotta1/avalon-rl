# Avalon Replay: product direction

## Decision

Make the failure-to-repair loop a primary Avalon capability.
A team supplies a failure and a correction. Replay turns them into an executable task and tests proposed repairs.
Keep the core local and open source.
Sell managed reconstruction, private execution, and accepted task delivery when customers request those services.
This business model is a hypothesis. No customer purchase validates it yet.

## The proposed customer promise

Turn an authorized coding failure into a task that accepts correct alternatives and retains evidence of failed repairs.
Measure the repair on separate inputs before accepting it.
Keep the failed baseline, reference, controls, candidate identity, execution image, and result together.

The first supported workload is a Python function with JSON arguments and results.
It is a deliberate product boundary. It does not cover arbitrary enterprise workflows.
The behavioral grader accepts implementations that return the required results without matching a reference file byte for byte.

## The expanded product

1. Capture failures through explicit agent integrations with source and permission records.
2. Reconstruct the smallest executable environment that preserves the failure.
3. Review requirements and validate graders with legitimate alternatives and negative controls.
4. Freeze task versions and independent evaluation inputs.
5. Run repair candidates or training policies under resource limits.
6. Compare results, latency, and complete costs with a named baseline.
7. Prepare authorized task packages for a specified buyer's acceptance process.
8. Record accepted deliveries and contributor compensation through an auditable commercial service.

The current release implements a bounded executable core and a development-only Gymnasium adapter.
Capture integrations, general environments, authenticated reviews, hosted training, and payment settlement remain separate builds.
Do not describe those future capabilities as shipped.

## What could make the business defensible

The hypothesis is a growing collection of authorized failures that repeatedly expose useful weaknesses in customer agents.
The collection must retain reconstruction knowledge, credible checks, and permission for the intended use.
File counts, synthetic difficulty, and GitHub activity do not establish that advantage.

A potential commercial unit is an accepted task family with replay evidence and agreed use rights.
A potential private product is managed repair evaluation for an agent team.
Neither unit has a validated price, margin, or repeat purchase rate in this implementation.

## The next customer experiment

Recruit five developers with one common workflow and permission to contribute failures.
Use twenty real failures and seek three prospective buyers or private evaluation customers.
These are proposed pilot targets, not observations or a statistical power calculation.

Compare Replay with a developer writing a regression test manually.
Record reconstruction minutes, review minutes, valid alternative acceptance, invalid solution rejection, and repeatable execution.
Record model fees, local compute costs, delivery costs, actual payments, and the time period.
Group related variants by source task and owner before separating development and evaluation cases.
Report paired results and uncertainty at the independent task-family level.
Keep negative findings and unaccepted submissions.

A paid delivery and repeated private use would improve the company case.
YC admission and media coverage remain external decisions.
